DeepGEMM — A Developer's Illustrated Guide

DeepGEMM is a unified, high-performance tensor-core kernel library for the matrix primitives that power modern large language models — FP8/FP4/BF16 GEMMs, fused MoE with overlapped NVLink communication ("Mega MoE"), MQA scoring for the lightning indexer, and HyperConnection. This guide is written for a CS graduate who is not a GPU-kernel expert: it explains the architecture, walks through the core GEMM path from Python call to hardware instruction, and defines the jargon along the way.

Hopper SM90 Blackwell SM100 Runtime JIT FP8 / FP4 / BF16 TMA + WGMMA/UMMA Mega MoE

01 High-Level Overview

The single sentence: DeepGEMM computes D = C + A @ B (and grouped/fused variants) on NVIDIA Hopper/Blackwell GPUs at near-peak tensor-core throughput, by generating one specialized CUDA kernel per problem shape at runtime.

What problem it solves

An LLM spends almost all its FLOPs in matrix multiplies — attention projections, FFN/MoE expert layers, and the tiny "indexer" scoring kernels. Doing these in FP8/FP4 (not BF16/FP16) doubles-to-quadruples the effective throughput and halves-to-quarters the weight memory. But FP8/FP4 GEMMs require per-block scaling-factor dequantization fused into the kernel, which cuBLAS does not expose cleanly. DeepGEMM ships purpose-built kernels for exactly this.

How it is organized

A thin Python package wraps a C++ extension (_C). The C++ layer never ships compiled kernels — instead it generates CUDA source strings at runtime, compiles them with nvcc/nvrtc, caches the .cubin on disk, and loads it as a CUfunction. This "JIT everything" design keeps the install footprint tiny while letting each (shape, dtype, tile-config) get a kernel specialized to its constants.

What it is not

It is not a general linear-algebra library. It supports a fixed set of memory layouts (NT/TN/NN/TT), fixed output dtypes (BF16 or FP32), and fixed scaling-factor "recipes". Input casting (BF16→FP8), transposition, and scale-factor quantization are left to the user (though helpers are provided). The focus is the kernel itself.

The unifying idea

A GEMM is tiled into blocks of (BLOCK_M × BLOCK_N × BLOCK_K). On each K-tile, TMA asynchronously copies A/B blocks (and their scaling factors) into shared memory; the tensor cores (WGMMA on Hopper, UMMA on Blackwell) consume them; an epilogue multiplies in the per-block FP8/FP4 scale factors and writes the BF16/FP32 result back via TMA. The whole loop is software-pipelined with async barriers so memory copy and math overlap. DeepGEMM's job is to pick the right tiles and generate the exact code for it.

02 Architecture at a Glance

A call descends through six layers. The top three live in Python and C++ host code; the bottom three live in the generated CUDA that runs on the GPU.

Figure 1. The six-layer descent of a single GEMM call. Layers ①–⑤ run on the CPU host (microseconds of overhead, cached after first call); layer ⑥ runs on the GPU.

Why two backends per family

Hopper (SM90, sm_90a) and Blackwell (SM100, sm_100a) have different tensor-core instructions and scaling support. On SM90 the FP8 scale factors are FP32 and the epilogue multiplies them into the accumulator in registers. On SM100 the scales are packed UE8M0 (a pure-power-of-2 exponent with no mantissa) and a block-scaled UMMA instruction applies them natively inside tensor memory (tmem). That is why you see twin files like sm90_fp8_gemm_1d1d.cuh and sm100_fp8_fp4_gemm_1d1d.cuh.

Two include trees — easy to confuse

Host headers live in csrc/ (compiled into _C.so at install time). Device kernels live in deep_gemm/include/deep_gemm/ and are not compiled at install — they are pulled in by #include from the JIT-generated source string at runtime. The develop.sh script symlinks CUTLASS/CuTe into deep_gemm/include/ so both the IDE and the JIT compiler can resolve <deep_gemm/...> and <cute/...>.

04 Build & Install Flow

A subtlety worth internalizing early: installation does not compile any GPU kernels. It only builds the thin pybind11 extension _C and bundles the device-kernel headers as package data.

install.sh → setup.py

setup.py:102-111, 168-214

Builds a CUDAExtension from the single source csrc/python_api.cpp, links cudart+nvrtc, and produces a wheel. CustomBuildPy first copies CUTLASS/CuTe headers into build_lib/deep_gemm/include, bakes persistent envs into envs.py (DG_JIT_CACHE_DIR, DG_JIT_CPP_STANDARD…), and regenerates _C.pyi. CachedWheelsCommand tries to download a prebuilt wheel matching (CUDA, torch, python, ABI) before falling back to a local build.

develop.sh (dev loop)

develop.sh

Symlinks cutlass/ and cute/ into deep_gemm/include/, runs python setup.py build, and symlinks the resulting _C.so into the package dir for in-place imports. Use this when editing C++ host code.

1

Install builds only the C++ glue

nvcc/nvrtc are not invoked at install. The device kernels (.cuh) are shipped verbatim inside the wheel as package_data (setup.py:201-207).

2

First call triggers JIT

When a GEMM is first called, Python's import deep_gemm has already run _C.init(library_root, cuda_home) (__init__.py:124), which records where the device headers and nvcc live. The call then descends to the host launcher, which emits a CUDA source string, hands it to the JIT compiler, and nvcc produces kernel.cubin.

3

Subsequent calls hit cache

The cubin is cached under ~/.deep_gemm/cache/kernel.<name>.<hash>/ and an in-process KernelRuntimeCache holds the loaded CUfunction. The second call with the same shape is just a cuLaunchKernelEx — effectively zero CPU overhead.

05 Per-Component Analysis

5.1 — The Python package deep_gemm/

The package is a thin façade. __init__.py (deep_gemm/__init__.py) does four things:

  1. Seed env vars from the build-time-baked envs.py (lines 6–13) so cache dir / C++ standard persist.
  2. Re-export the C++ symbols from _C — every kernel (fp8_gemm_nt, bf16_gemm_nt, fp8_fp4_mega_moe…) is a C++ function bound by pybind11 (lines 16–83). FP8 names are aliased to the FP8×FP4 implementations (fp8_gemm_nt = fp8_fp4_gemm_nt, see gemm.hpp:711-717).
  3. Import the mega helpers from .mega (lines 86–92) — pure-Python orchestration around symmetric memory.
  4. Locate CUDA and call _C.init() (lines 106–127) so the C++ side knows where nvcc and the device headers are.

utils/math.py — quantization

deep_gemm/utils/math.py

The user-facing FP8/FP4 casters: per_token_cast_to_fp8 (line 26), per_token_cast_to_fp4 (line 96), per_channel_cast_to_fp8, per_block_cast_to_fp8. Each splits the tensor into gran_k-element groups, computes the group amax, derives the scale sf = amax / 448.0 (FP8 max) or amax / 6.0 (FP4 max), optionally rounds it to UE8M0 via ceil_to_ue8m0 (line 13), and packs 4 scales into one int32 via pack_ue8m0_to_int (line 19). cast_back_from_fp8/fp4 provides the reference dequantizer used in tests.

mega/__init__.py — MoE orchestration

deep_gemm/mega/__init__.py

SymmBuffer (line 18) allocates a symmetric-memory buffer across a torch.distributed group and carves it into named views (x, l1_acts, l2_acts, their SFs…) using the slice_input_buffers closure returned by C++. transform_weights_for_mega_moe (line 131) interleaves gate/up weight rows and transposes the FP4 SFs for the UTCCP load path. The thin Python fp8_fp4_mega_moe (line 153) just forwards to _C.fp8_fp4_mega_moe.

utils/dist.py — distributed setup

deep_gemm/utils/dist.py

init_dist (line 10) bootstraps an NCCL process group; uneven_all_gather handles variable-length gathers. The actual symmetric-memory rendezvous is delegated to torch.distributed._symmetric_memory inside SymmBuffer.

testing/{numeric,bench}.py

deep_gemm/testing/numeric.py

calc_diff (line 5) computes a cosine-like relative error 1 − 2⟨x,y⟩/(‖x‖²+‖y‖²); assert_bitwise_equal (line 24) does exact byte comparison for SF packing tests. bench.py measures TFLOPS and bandwidth over increasing M.

5.2 — The C++ API layer csrc/apis/

One header per feature family, each exposing a register_apis(pybind11::module_&) called from python_api.cpp:17-28:

// csrc/python_api.cpp
PYBIND11_MODULE(_C, m) {
    m.doc() = "DeepGEMM C++ library";
    deep_gemm::attention::register_apis(m);     // MQA logits, head-split GEMM
    deep_gemm::einsum::register_apis(m);        // hardcoded BF16/FP8 contractions
    deep_gemm::hyperconnection::register_apis(m);
    deep_gemm::gemm::register_apis(m);           // the big one: dense/grouped GEMMs
    deep_gemm::layout::register_apis(m);         // SF layout transforms
    deep_gemm::mega::register_apis(m);           // Mega MoE
    deep_gemm::runtime::register_apis(m);        // set_num_sms, set_pdl, init()
}

The API functions are deliberately uniform: they (1) read tensor majors/shapes, (2) validate, (3) transform the scaling factors into the layout the hardware wants, (4) branch on architecture, and (5) call into the host launcher. The dense FP8 entry is the canonical example:

// csrc/apis/gemm.hpp:73
static void fp8_fp4_gemm_nt(const pair<Tensor,Tensor>& a, const pair<Tensor,Tensor>& b,
                      Tensor& d, optional<Tensor> c, recipe…, compiled_dims, disable_ue8m0_cast) {
    const auto major_a = get_major_type_ab(a.first);   // K-major or MN-major
    const auto [m,k]  = check_ab_fp8_fp4(a.first, major_a, arch_major);
    const auto [n,k_]= check_ab_fp8_fp4(b.first, major_b, arch_major);
    if (early_return(m,n,k,d,c)) return;

    // Turn the user's FP32 SFs into the hardware-required layout (TMA-aligned, MN-major, packed UE8M0 on SM100)
    auto [sfa,sfb,gran_k_a,gran_k_b] =
        layout::transform_sf_pair_into_required_layout(a.second,b.second,m,n,k,recipe,…,disable_ue8m0_cast);

    if (arch_major==9 and sfa.scalar_type()==kFloat)        sm90_fp8_gemm_1d1d(a.first,sfa,b.first,sfb,c,d,m,n,k,major_a,major_b,compiled_dims);
    else if (arch_major==10 and sfa.scalar_type()==kInt)  sm100_fp8_fp4_gemm_1d1d(a.first,sfa,b.first,sfb,c,d,…,compiled_dims);
}

Notice the layout-transform step is shared across families via layout::transform_sf_pair_into_required_layout (apis/layout.hpp:63), and the "recipe" (a 3-tuple (gran_mn, gran_mn, gran_k)) encodes the scaling-factor blocking. The NN/TN/TT variants are one-liners that transpose operands and delegate to _nt (gemm.hpp:126-164).

The "recipe" abstraction

A GEMM's scaling factors can be quantized at different granularities. DeepGEMM encodes this as a tuple (gran_mn_A, gran_mn_B, gran_k). The default recipes are (1,128,128) on SM90 (per-row A scale, per-128-channel B scale, 128-K grouping — the "1D2D" kernel) and (1,1,128) on SM100 (per-row on both — the "1D1D" kernel) (utils/layout.hpp:74-87). gran_k is almost always 128 (or 32 for FP4) because that is the natural FP8 MMA block size.

5.3 — The JIT compiler csrc/jit/

This is the cleverest part of the design. Five small files implement a complete runtime compilation pipeline.

compiler.hpp

csrc/jit/compiler.hpp

Base Compiler + NVCCCompiler (line 171, shells out to nvcc -cubin) and NVRTCCompiler (line 254, in-process compile via libnvrtc, ~10× faster, opt-in with DG_JIT_USE_NVRTC=1). The build(name, code) method (line 100) is the entry point: it hashes name$signature$flags$code, checks an in-process cache, compiles into a temp dir, then atomically renames the directory into the cache path (crash-safe on shared filesystems).

kernel_runtime.hpp

csrc/jit/kernel_runtime.hpp

KernelRuntime (line 28) loads kernel.cubin into a CUlibrary/CUfunction via load_kernel, enumerating the single kernel symbol (or using cuLibraryEnumerateKernels on newer drivers). LaunchRuntime<Derived> (line 119) is the CRTP base every host launcher inherits: generate() prepends an include-hash comment, launch() builds the dim3/cluster/PDL config and calls Derived::launch_impl.

handle.hpp

csrc/jit/handle.hpp

Lazy-loads CUDA driver symbols (lazy_cuLaunchKernelEx, lazy_cuTensorMapEncodeTiled…) via dlopen. Provides load_kernel, construct_launch_config (sets cluster + PDL launch attributes), and launch_kernel (packs variadic args into void*[]).

cache.hpp

csrc/jit/cache.hpp

KernelRuntimeCache — a process-lifetime unordered_map<path, shared_ptr<KernelRuntime>>. get() returns the loaded function if the dir is valid, else constructs one.

include_parser.hpp

csrc/jit/include_parser.hpp

Recursively hashes every #include <deep_gemm/...> reached from the generated source. That hash is baked into the cache key, so editing any .cuh invalidates only affected kernels.

device_runtime.hpp holds the DeviceRuntime singleton: device props, arch detection (get_arch returns 90a/100a/100f), and the runtime knobs (num_sms, tc_util, enable_pdl) exposed to Python. apis/runtime.hpp wires them and the init() call (apis/runtime.hpp:42-48).

5.4 — The heuristics engine csrc/jit_kernels/heuristics/

"Heuristics" = picking the tile sizes and pipeline depth for a given (shape, dtype, arch). It is a small enumerate-and-score search, not machine learning.

// heuristics/common.hpp:14
template<typename ArchSpec>
GemmConfig get_best_config(const GemmDesc& desc) {
    auto candidates = ArchSpec::get_layout_candidates(desc);   // enumerate (block_m,block_n,cluster) combos
    auto best = candidates[0], best_info = ArchSpec::get_layout_info(desc, best);
    for (auto& c : candidates)                                   // score each by an estimated cycle count
        if (ArchSpec::compare(info, best_info)) best = c;
    return { best, ArchSpec::get_storage_config(desc,best),
              ArchSpec::get_pipeline_config(desc,best,sc), ArchSpec::get_launch_config(desc,best) };
}

sm90.hpp — Hopper

heuristics/sm90.hpp:13

Enumerates block_m∈{16,32,64,128,256}, block_n∈[16..256], cluster∈{1,2} with legality filters (swizzle ≥ 64B, ≥3 stages, no multicast if single wave). Scores by an analytical L1/L2 cycle model (get_layout_info, line 201): it estimates bytes moved per block through L1 and L2 and divides by their per-cycle bandwidths. block_k = 128 / elem_size (so 128 for FP8, 64 for BF16).

sm100.hpp — Blackwell

heuristics/sm100.hpp:14

Same shape but adds swap_ab (transposes A/B to fit the UMMA layout), enforces UTCCP-128 SF alignment (get_sf_uttcp_aligned_block_sizes), checks tensor-memory column budget (2*umma_n + tmem_sf_cols ≤ 512), and prefers larger clusters and single-wave configs. The comparator is a preference cascade (single-wave > multicast > fewer waves > larger last-wave util > smaller tiles).

heuristics/runtime.hpp holds tunables settable from Python: set_block_size_multiple_of, set_ignore_compile_dims, and the contiguous-layout M/K alignment (default 128, can shrink to 32 on SM100 — runtime.hpp:47).

5.5 — The host launchers csrc/jit_kernels/impls/*.hpp

Each .hpp here is the bridge between "a validated GEMM" and "a launched GPU kernel". It defines a LaunchRuntime-derived class whose generate_impl() returns the CUDA source string and whose launch_impl() issues the driver launch. Take the SM90 FP8 1D1D launcher:

// csrc/jit_kernels/impls/sm90_fp8_gemm_1d1d.hpp:15
class SM90FP8Gemm1D1DRuntime final : public LaunchRuntime<SM90FP8Gemm1D1DRuntime> {
    struct Args { GemmDesc gemm_desc; GemmConfig gemm_config; LaunchArgs launch_args;
              void* gmem_a_ptr; …; CUtensorMap tensor_map_a_base, tensor_map_b_base,
                                              tensor_map_sfa, tensor_map_sfb, tensor_map_cd; };

    static string generate_impl(const Args& a) {
        return fmt::format(R"(
#include <deep_gemm/impls/sm90_fp8_gemm_1d1d.cuh>
static void __instantiate_kernel() {{
    auto ptr = &sm90_fp8_gemm_1d1d_impl<{m},{n},{k}, {num_groups}, {block_m},{block_n},{block_k},
        {sw_a},{sw_b}, {stages}, {tma_thr},{math_thr}, {cluster},{mcast}, {num_sms}, {gemm_type}, {cd_dtype}>;
}})", …);                       // bake the heuristics constants AS TEMPLATE ARGS
    }
    static void launch_impl(kernel, config, args) {
        launch_kernel(kernel, config, args.gmem_a_ptr, …, args.gemm_desc.m,n,k,
                      args.tensor_map_a_base, …, args.tensor_map_cd);
    }
};
Why bake constants as template arguments?

The device kernel is a giant C++ template sm90_fp8_gemm_1d1d_impl<SHAPE_M,SHAPE_N,…,BLOCK_M,…>. By formatting the heuristics-chosen values directly into the source as integer template parameters, nvcc sees them as compile-time constants and fully unrolls loops, folds branches, and pre-computes shared-memory offsets. The runtime-varying values (actual m,n,k for the not-compiled dims, data pointers, TMA descriptors) are passed as ordinary kernel arguments. The compiled_dims="nk" flag controls which of m/n/k become template constants vs. runtime args — compiling more dims = faster kernel but a fresh cubin per shape.

The free function sm90_fp8_gemm_1d1d() (line 78) is what the API calls. It builds the GemmDesc, calls get_best_config<SM90ArchSpec>, constructs the five TMA descriptors (next subsection), packs Args, calls generate → compiler->build → launch.

5.6 — The device kernels deep_gemm/include/deep_gemm/

These are the actual GPU code. They are #included by the JIT source and never compiled at install time. The directory mirrors the host side:

  • impls/ — the templated kernel bodies (sm90_fp8_gemm_1d1d.cuh, sm100_fp8_fp4_gemm_1d1d.cuh, sm100_fp8_fp4_mega_moe.cuh, sm100_mqa_logits.cuh…).
  • mma/ — thin wrappers over the tensor-core instructions: wgmma (Hopper, mma/sm90.cuh) and the UMMA descriptor builders (Blackwell, mma/sm100.cuh, including make_sf_desc for the UTCCP SF layout).
  • ptx/ — raw inline-PTX intrinsics (tma.cuh for async copy, wgmma.cuh, tcgen05.cuh for Blackwell tensor-memory ops, ld_st.cuh for shared-memory loads/stores).
  • scheduler/ — the Scheduler that maps blocks to (M,N) tiles with L2-friendly swizzling, and handles grouped/masked/psum layouts (scheduler/gemm.cuh).
  • epilogue/ — the result write-back: transform.cuh (head-split index remap) and sm100_store_cd.cuh (tmem→smem→TMA-store with BF16 cast).
  • comm/barrier.cuh, common/{math,utils,tma_copy,types}.cuh — shared utilities.

The FP8 1D1D kernel signature shows the full contract (impls/sm90_fp8_gemm_1d1d.cuh:30):

template<uint SHAPE_M,SHAPE_N,SHAPE_K, kNumGroups, BLOCK_M,BLOCK_N,BLOCK_K,
          kSwizzleAMode,kSwizzleBMode, kNumStages, kNumTMAThreads,kNumMathThreads,
          kNumTMAMulticast,kIsTMAMulticastOnA, kNumSMs, GemmType kGemmType, typename cd_dtype_t>
__global__ void sm90_fp8_gemm_1d1d_impl(

Almost everything the kernel needs is baked into template params; the runtime args are the few not-compiled dims, the data pointers, and the five TMA descriptors (passed as __grid_constant__ so they live in constant memory).

SM90 epilogue: register promotion

sm90_fp8_gemm_1d1d.cuh:311-320

Hopper's WGMMA produces an FP32 accumulator accum[] per K-tile. Because the inputs were FP8 (no native block-scaled MMA), the kernel keeps a separate final_accum[] and, after each K-tile's WGMMA completes, reads the per-block FP32 scales scale_a_0/1 (from smem_sfa) and scales_b[] (from smem_sfb) and does final_accum += scale_a * scale_b * accum. The result goes to smem then a TMA-reduce-add store accumulates split-K partials into D.

SM100 epilogue: native block-scaled UMMA

sm100_fp8_fp4_gemm_1d1d.cuh:285

Blackwell has a block-scaled MMA instruction. The kernel builds cute::UMMA::make_instr_desc_block_scaled<…, float, float_ue8m0_t, …> (line 285) and copies the packed-UE8M0 SFA/SFB into tensor memory columns (kTmemStartColOfSFA/SFB) via the UTCCP copy (lines 358/367). The hardware then multiplies SFA·SFB·accum natively. The epilogue (epilogue/sm100_store_cd.cuh) just drains tmem→smem, optionally casts to BF16, and TMA-stores.

5.7 — Mega MoE csrc/apis/mega.hpp + impls/sm100_fp8_fp4_mega_moe.cuh

Mega MoE is the headline feature: a single kernel that fuses the entire routed-expert FFN of an MoE layer and overlaps the NVLink token dispatch/combine with the two GEMMs.

Figure 2. Mega MoE fuses EP dispatch + GEMM1 + SwiGLU + GEMM2 + EP combine and overlaps NVLink with tensor-core math.

Symmetric memory

mega/__init__.py:18, apis/mega.hpp:34

Each rank allocates a buffer of equal size; symm_mem.rendezvous registers it so every rank can read/write every other rank's buffer directly over NVLink (peer-to-peer). sym_buffer_ptrs is the list of device pointers across ranks passed into the kernel. The C++ get_symm_buffer_size_for_mega_moe computes the worst-case ring-buffer capacity over all candidate BLOCK_M and returns a slicing closure that carves the flat buffer into the named sub-buffers.

Weight transform

mega/__init__.py:97-149

transform_weights_for_mega_moe interleaves gate/up rows (_interleave_weights, so SwiGLU can read them as one packed tensor) and transposes the FP4 SFs into the UTCCP-friendly layout (_transpose_sf_for_utccp). L1 weights get both; L2 only the SF transpose.

The heuristics (heuristics/mega_moe.hpp:76) pick block_m from the expected tokens-per-expert (8→16→32→64→96→192), always cluster-2, block_n=128, and compute pipeline depth from the SM100 shared-memory budget. The ring-buffer layout lives in layout/mega_moe.cuh (MegaMoEBuffer with its Workspace of NVLink/grid/expert counters).

csrc/utils/{hash,system,lazy_init,…}

06 Core Workflow Walkthrough: fp8_gemm_nt end-to-end

Follow one call — deep_gemm.fp8_gemm_nt(a, b, d, c) with a,b FP8+E4M3, d BF16, on an H100 — from the Python statement to the PTX instruction. Eight steps.

1

Python entry & symbol resolution

The user calls deep_gemm.fp8_gemm_nt. In __init__.py:711… actually the alias is set in C++: m.attr("fp8_gemm_nt") = m.attr("fp8_fp4_gemm_nt") (gemm.hpp:711). So the call lands in fp8_fp4_gemm_nt in apis/gemm.hpp:73. (On SM90 the SF dtype is FP32; on SM100 the user would supply packed-int UE8M0, dispatching to the SM100 path.)

2

Validation & scaling-factor layout transform

The API reads the major-ness of a/b (K-major required on SM90), checks shapes/types, handles the trivial k==0 / accumulation-copy cases (early_return, gemm.hpp:19), then calls layout::transform_sf_pair_into_required_layout (apis/layout.hpp:63).

For SM90 + FP32 SF + recipe (1,128,128) this is the 1D2D path: SFA becomes MN-major-TMA-aligned (get_mn_major_tma_aligned_tensor), SFB stays contiguous. For SM100 the FP32 scales are rounded to UE8M0, packed 4-per-int32, and made MN-major/TMA-aligned (get_mn_major_tma_aligned_packed_ue8m0_tensor, apis/layout.hpp:49-54). The returned gran_k_a/b tell the launcher which kernel variant to instantiate.

Then it dispatches: SM90 sm90_fp8_gemm_1d1d (when gran_n==1) or sm90_fp8_gemm_1d2d; SM100 sm100_fp8_fp4_gemm_1d1d (gemm.hpp:110-123).

3

Heuristic tuning

The launcher sm90_fp8_gemm_1d1d (impls/sm90_fp8_gemm_1d1d.hpp:78) builds a GemmDesc with gemm_type=Normal, kernel_type=Kernel1D1D and calls get_best_config<SM90ArchSpec>(desc) (heuristics/common.hpp:14).

For our shape, the search enumerates candidate (block_m, block_n, cluster), scores each by the L1/L2 cycle model, and returns e.g. block_m=128, block_n=128, block_k=128, num_stages=4, cluster=2, num_threads=384. block_k is fixed at 128/elem_size = 128 for FP8 (sm90.hpp:60). The config also fixes the swizzle modes (here both 128B) and asserts there are no TMA splits (impls/sm90_fp8_gemm_1d1d.hpp:102-103).

4

TMA descriptor construction

Five CUtensorMap objects are built on the host via lazy_cuTensorMapEncodeTiled (impls/runtime_utils.hpp:144):

  • tensor_map_a / tensor_map_b — describe A/B in global memory with the chosen swizzle, so a single TMA instruction fetches a whole block_m×block_k tile.
  • tensor_map_sfa / tensor_map_sfb — describe the (now-transformed) scale-factor tensors in MN-major TMA-aligned form (make_tma_sf_desc, runtime_utils.hpp:247).
  • tensor_map_cd — describes D (and C via reduce-add) for the TMA store/reduce epilogue.

These are passed to the kernel as __grid_constant__ (placed in constant memory) — TMA needs the descriptor resident, not a pointer to it.

5

JIT source generation

SM90FP8Gemm1D1DRuntime::generate_impl (impls/sm90_fp8_gemm_1d1d.hpp:33) fmt::formats a tiny CUDA source that #includes the device kernel <deep_gemm/impls/sm90_fp8_gemm_1d1d.cuh> and then references the kernel template instantiated with the heuristics values as integer template arguments. LaunchRuntime::generate (kernel_runtime.hpp:122) prepends the recursive include-hash so any header edit invalidates the cache. The resulting string is e.g.:

// Includes' hash value: 3f2a…
#include <deep_gemm/impls/sm90_fp8_gemm_1d1d.cuh>
static void __instantiate_kernel() {
    auto ptr = &sm90_fp8_gemm_1d1d_impl<0,0,0, 1, 128,128,128, 128,128, 4, 128,256, 2,0, 132, GemmType::Normal, float>;
}

The 0,0,0 for SHAPE_M/N/K means compiled_dims="nk" would make some of them constants; here the default "nk" bakes M and K as constants if the API passed real shapes — the launcher uses get_compiled_dim (runtime_utils.hpp:22) to decide per-dimension.

6

Compile & cache lookup

compiler->build("sm90_fp8_gemm_1d1d", code) (compiler.hpp:100):

  1. Hash "sm90_fp8_gemm_1d1d$$NVCC12.9$$<flags>$$<code>" → cache dir ~/.deep_gemm/cache/kernel.sm90_fp8_gemm_1d1d.<hash>/.
  2. If the in-process KernelRuntimeCache has it (cache.hpp:18), return immediately.
  3. Otherwise shell out: cd <tmp> && nvcc kernel.cu -cubin -o kernel.cubin --gpu-architecture=sm_90a -O3 … (compiler.hpp:221). On failure the assertion prints the NVCC log.
  4. fsync the temp dir and atomically rename it to the cache path (concurrent-safe).
  5. Construct a KernelRuntime: cuLibraryLoadFromFile → cuLibraryEnumerateKernels → cuKernelGetFunction (handle.hpp:135). Store in the cache; return the shared_ptr.

Second call with the same shape skips steps 3–5 entirely.

7

Kernel launch

SM90FP8Gemm1D1DRuntime::launch(runtime, args) (kernel_runtime.hpp:138) builds a LaunchConfig with grid = (num_sms, 1), block = (num_threads,), cluster = 2, and the PDL flag (from device_runtime->get_pdl()). construct_launch_config (handle.hpp:174) sets the cluster-dimension and programmatic-stream-serialization launch attributes, then launch_kernel packs the 13 kernel args (pointers, m/n/k, five TMA descriptors) into a void*[] and calls cuLaunchKernelEx.

8

Inside the device kernel

Now on the GPU. The kernel (impls/sm90_fp8_gemm_1d1d.cuh:30) splits its threads into a TMA producer warpgroup (the last 128 threads) and math consumer warpgroups (the first 256), which synchronize through async ClusterTransactionBarriers in shared memory.

Figure 3. The producer/consumer pipeline of one output tile. The K-loop is software-pipelined: while the consumer does WGMMA on stage s, the producer TMA-loads stage s+1..s+N.

The mechanics, in order (sm90_fp8_gemm_1d1d.cuh):

  1. Prefetch + barrier init (lines 83-148): one thread prefetches the five TMA descriptors into the async proxy; one warpgroup initializes kNumStages full/empty barrier pairs. Register counts are reconfigured (warpgroup_reg_alloc/dealloc) to give the math side maximum registers.
  2. Scheduler (line 162): Scheduler<Normal,…> (scheduler/gemm.cuh:197) hands out (m_block, n_block) tiles via L2-swizzled persistent scheduling — each SM keeps grabbing tiles until none remain. For grouped/masked variants the same scheduler walks the group layout.
  3. Producer K-loop (lines 170-245): for each K-block, wait on the empty barrier for a free stage, issue four TMAs (SFA, SFB, A-swizzled, B-swizzled) into that stage's smem, then full_barrier.arrive_and_expect_tx(total_bytes) so the consumer knows when the copy lands.
  4. Consumer K-loop (lines 246-321): wait on the full barrier; load the per-row scales scale_a_0/1 and per-channel scales_b[] from smem; fence accumulators; issue warpgroup_arrive + a loop of WGMMA::wgmma(desc_a, desc_b, accum, k) (the Hopper tensor-core op) over BLOCK_K/WGMMA::K sub-tiles; warpgroup_commit_batch + warpgroup_wait<0>; arrive on the empty barrier; then the promotion final_accum[i] += scale_a * scale_b * accum[i] (lines 311-320).
  5. Epilogue store (lines 323-347): write final_accum into smem_d, then one elected thread issues SM90_TMA_REDUCE_ADD_2D::copy which atomically adds the tile into global D (and C, since the kernel accumulates D = C + …). The reduce-add is what makes split-K and multi-CTA overlap safe.

On Blackwell (sm100_fp8_fp4_gemm_1d1d.cuh) the structure is analogous but the promotion step disappears from registers: the block-scaled UMMA instruction (line 285) consumes SFA/SFB from tensor memory and writes the scaled result directly, and the epilogue (epilogue/sm100_store_cd.cuh) drains tmem → smem → TMA store with an optional BF16 cast.

Where the "D = C + A @ B" actually happens

In math: D[i,j] = C[i,j] + Σ_k (A[i,k]·sfa[i,k]) · (B[j,k]·sfb[j,k]). The FP8 A·B is accumulated by WGMMA into accum per K-tile; the sfa·sfb multiply and the accumulation across K-tiles is the epilogue promotion; the + C is the TMA reduce-add into D. So the whole GEMM is split across three hardware units (TMA copy engine, tensor cores, TMA store/reduce) running concurrently behind async barriers.

07 Mega MoE Walkthrough

A multi-process Mega MoE call. The setup is heavier than a plain GEMM because it must coordinate symmetric memory and weight layouts across ranks once, then the per-step call is cheap.

A

One-time setup (per rank)

init_dist bootstraps NCCL (utils/dist.py:10). Then get_symm_buffer_for_mega_moe (mega/__init__.py:69) aligns the token count to get_token_alignment_for_mega_moe() (= 384, the LCM of candidate block sizes) and constructs a SymmBuffer. The constructor asks C++ get_symm_buffer_size_for_mega_moe (apis/mega.hpp:34) for the byte size + a slicing closure, allocates an int8 buffer, and (for >1 rank) calls symm_mem.rendezvous to register it for peer access. The closure carves the flat buffer into x, x_sf, topk_idx, topk_weights, l1_acts(+sf), l2_acts(+sf), combine_token_buffer and (optionally) shared-expert buffers (layout/mega_moe.cuh:331).

B

Weight preparation (once)

transform_weights_for_mega_moe(l1, l2) (mega/__init__.py:131): for FP8×FP4, interleave gate/up rows of W1 and its SF, transpose W1's SF for UTCCP; for W2 only transpose the SF. The transformed (weight, SF) tuples are what get passed every call.

C

Per-step call

The user copies x_fp8, x_sf, topk_idx, topk_weights into the buffer views, then calls deep_gemm.fp8_fp4_mega_moe(y, transformed_l1, transformed_l2, sym_buffer, …) (mega/__init__.py:153), which forwards to _C.fp8_fp4_mega_moe (apis/mega.hpp:157). That function validates everything (recipe (1,1,32), SwiGLU, SF layout) and dispatches to sm100_fp8_fp4_mega_moe.

D

Inside the mega-kernel

The device kernel (impls/sm100_fp8_fp4_mega_moe.cuh) is the largest file in the repo (~1,460 lines). It runs as a single grid with distinct thread roles:

  • Dispatch warps pull tokens from the local x buffer and ship them to the owning rank's l1_acts ring slot for each chosen expert (over NVLink, using the symmetric buffer + sym_buffer_ptrs).
  • Math warps consume ready l1_acts tiles, run GEMM1 (FP8×FP4, block-scaled UMMA), apply SwiGLU (+ cross-warp amax reduction for the next FP8 quantization), run GEMM2 into l2_acts→y.
  • Combine warps write finished expert outputs back to the origin rank/token via NVLink and accumulate with topk_weights.

Coordination is via the Workspace counters in the symmetric buffer (layout/mega_moe.cuh:46): expert send/recv counts, ring full/empty block counts, NVLink barrier signals, and L1/L2 schedule task counters — all laid out to avoid L2-line ping-ponging on hot atomics. The ring-buffer capacity (num_ring_tokens) is sized so the math side never stalls waiting for tokens to arrive (heuristics/mega_moe.hpp:115).

Why "overlapped" matters

A naive MoE does dispatch → GEMM1 → act → GEMM2 → combine as four sequential steps, so the NVLink is idle during math and the tensor cores are idle during communication. Mega MoE pipelines them: while GEMM1 computes token-block t, dispatch is sending blocks t+1,t+2 and combine is finishing blocks t-1. On a multi-node EP this turns the communication from a serialization bottleneck into mostly-hidden overhead — the headline latency win.

08 Terminology Glossary

GPU-kernel jargon, defined for someone who knows CS but not CUDA. Roughly in the order you will meet them.

GEMM
General Matrix Multiply. D = C + A @ B. The dominant compute kernel in deep learning.
NT / TN / NN / TT
The memory layout of the two operands: NT = A non-transposed (row-major), B transposed (column-major). DeepGEMM's reference is NT: [M,K] @ [N,K].T. The others are implemented by transposing operands and calling _nt (gemm.hpp:126-164).
Major (K-major / MN-major)
Which dimension is contiguous in memory. "K-major" = the K axis stride is 1 (row-major in the natural [M,K] view). Decides the TMA descriptor shape and the MMA descriptor type (utils/layout.hpp:21).
FP8 E4M3
An 8-bit float with 4 exponent bits and 3 mantissa bits (±, E4M3). Max representable ≈ 448. Used for activations and weights. Stored as torch.float8_e4m3fn.
FP4 E2M1
A 4-bit float (2 exponent, 1 mantissa). Max ≈ 6. Two FP4 values are packed into one byte ("packed FP4", int8). DeepGEMM uses FP4 for MoE weights on SM100.
Scaling factor (SF / SFA / SFB)
A per-group multiplier that restores the real value from the quantized one: real ≈ fp8_value × sf. SFA scales A (per-token rows), SFB scales B (per-channel columns). Stored separately from the data as a small tensor.
UE8M0
"Unsigned Exponent, 8 bits, 0 mantissa bits" — a scaling factor that is a pure power of two (2^e). It is just the 8 exponent bits of an IEEE float with a zero mantissa, so it can be packed four per int32. SM100's block-scaled MMA consumes this format natively (utils/math.py:13-24).
Recipe
A tuple (gran_mn_A, gran_mn_B, gran_k) giving the scaling-factor blocking: SFA is quantized with one scale per gran_mn_A rows and gran_k K-elements. (1,1,128) = "1D1D" (per-row on both sides); (1,128,128) = "1D2D".
1D1D / 1D2D kernel
The SF memory layout the kernel expects. 1D1D = both SFA and SFB are 1D (per-row) and loaded with their own TMA. 1D2D = SFB is a 2D table (per-128-channel), kept in registers across the K-loop. SM100 standardizes on 1D1D; SM90 supports both (gemm.hpp:110-117).
Granularity (gran_k)
The K-axis size of one scaling group — almost always 128 (FP8 natural block) or 32 (FP4).
Tensor Cores
Dedicated matrix-multiply units on the GPU. Hopper's are driven by WGMMA ("warpgroup MMA"); Blackwell's by UMMA ("unified MMA", which also has a block-scaled variant).
TMA
"Tensor Memory Accelerator" — a copy engine that moves 2D/3D tiles between HBM and shared memory asynchronously, with hardware swizzling and out-of-bounds fill, described by a CUtensorMap descriptor. Frees the SM to compute while data loads.
Swizzling
Reordering bytes within a shared-memory tile to avoid bank conflicts. Modes are 16/32/64/128B; DeepGEMM requires ≥64B (128B for FP4) for performance (heuristics/utils.hpp:13).
Shared memory (smem)
Small, fast on-chip RAM shared by a thread block. The A/B/SF tiles live here between TMA load and tensor-core consume; the epilogue stages results here before the TMA store.
Tensor memory (tmem)
Blackwell-specific on-chip storage dedicated to the tensor cores (distinct from smem). UMMA accumulates here, and the block-scaled scales are loaded here via UTCCP.
Software pipelining / num_stages
Keeping N copies ("stages") of the A/B tile in smem so that while the math consumes stage s, TMA loads stage s+1…s+N. Synchronized by full/empty async barriers. More stages hide more latency but use more smem (heuristics/sm90.hpp:148).
Async barrier
A hardware synchronization primitive (ClusterTransactionBarrier): the producer "arrives and expects N transaction bytes", the consumer "waits" until those bytes landed. Lets copy and math overlap without a global __syncthreads.
Warpgroup
4 warps (128 threads) acting as one unit. WGMMA/UMMA operate at warpgroup granularity.
Cluster
A group of 2 (Hopper) or 2–4 (Blackwell) thread blocks that share distributed shared memory and can TMA-multicast one load to all members. cluster_m/n in the Layout controls this.
PDL
"Programmatic Dependent Launch" — a launch attribute letting this kernel begin executing before the previous one fully finishes, with an explicit cudaGridDependencySynchronize() handoff. Reduces gap between back-to-back kernels (set_pdl, handle.hpp:206).
compiled_dims
Which of m/n/k are baked into the kernel as compile-time constants vs. runtime args. "nk" = M and K are constants (one cubin per (M,K)); "" = fully generic. More compiled dims = faster but more cubins to cache (runtime_utils.hpp:22).
tc_util
"Tensor-core utilization" ratio (0–100). A runtime knob to throttle how many SMs run math, leaving headroom for concurrent workloads (device_runtime.hpp:118).
MoE / Expert / Top-k
"Mixture of Experts": a layer where a router picks topk experts per token and only those experts' FFN weights apply. "Routed" experts are partitioned across ranks (EP).
EP (Expert Parallel) / dispatch / combine
EP shards experts across GPUs. Dispatch = sending each token to the rank(s) holding its chosen experts. Combine = gathering expert outputs back and summing with topk_weights. These are the NVLink communication steps Mega MoE overlaps with math.
Symmetric memory
A buffer allocated identically on every rank and registered for direct peer-to-peer access, so a kernel on rank A can read/write rank B's buffer over NVLink without going through a separate copy.
SwiGLU
The FFN activation swish(W1·x) * (W3·x); implemented by interleaving gate/up weight rows so one GEMM produces both halves (mega/__init__.py:97).
MQA / indexer
"Multi-Query Attention" with one KV head. DeepSeek v3.2's "lightning indexer" uses a weighted-ReLU variant: out[i,j] = Σ_h relu(q[i,h]·kv[j,h]) * w[i,h] (apis/attention.hpp:76).
HyperConnection (HC)
A normalization scheme; tf32_hc_prenorm_gemm fuses a TF32 GEMM with the HC pre-normalization (apis/hyperconnection.hpp).
psum layout
"Partial-sum" contiguous layout for grouped GEMMs where group boundaries do not align to BLOCK_M; padding rows are skipped via the scheduler (scheduler/gemm.cuh:217).

10 How to Explore Further

A suggested reading path through the source, from gentlest to deepest.

  1. Run a test. tests/test_fp8_fp4.py shows the canonical quantize → GEMM → dequantize → compare loop. tests/test_mega_moe.py shows the full multi-process Mega MoE setup. Run with DG_JIT_DEBUG=1 to see the generated source and launch config printed.
  2. Read one API. csrc/apis/gemm.hpp:73 (fp8_fp4_gemm_nt) — it is the template every other family follows: validate → transform SF → dispatch.
  3. Read one launcher. csrc/jit_kernels/impls/sm90_fp8_gemm_1d1d.hpp — the smallest complete example of "heuristics → TMA → codegen → launch".
  4. Read the JIT core. csrc/jit/compiler.hpp + kernel_runtime.hpp + handle.hpp — only ~600 lines total and self-contained.
  5. Read one device kernel. deep_gemm/include/deep_gemm/impls/sm90_fp8_gemm_1d1d.cuh (357 lines) — the producer/consumer pipeline is clearest here because the promotion is in plain C++.
  6. Then the SM100 counterpart. sm100_fp8_fp4_gemm_1d1d.cuh to see how tmem + block-scaled UMMA replaces the manual promotion.
  7. Finally the mega-kernel. impls/sm100_fp8_fp4_mega_moe.cuh — the culmination of everything above (NVLink + two GEMMs + activation + combine in one grid).
The mental model to hold onto

DeepGEMM = (a) a small set of templated, near-optimal GPU kernels, where the template parameters are the "interesting" tuning choices; (b) a host heuristic that picks those parameters per shape; and (c) a runtime JIT that specializes and caches the kernel. Everything else — the Python package, the SF layout transforms, the symmetric-memory orchestration — exists to feed correct, well-laid-out data into (a). When something looks complicated, ask which of those three it belongs to.
